Automate what should not need a human

The goal of DevOps is not to automate everything. It is to automate what should not need a person every time, and to keep a person where judgment matters.

November 12, 2026 · 5 min read

I do not think anyone became a DevOps engineer to repeat the same tasks daily. Manual deployments, updating servers by hand, and troubleshooting the same problem again are easy habits to fall into. But the answer is not more scripts. It is the right automation.

What good automation does

  • Reduces repetitive work.
  • Catches failures early.
  • Recovers from common problems by itself.
  • Notifies you only when you need to get involved.

Bad automation does the opposite. It creates noise, breaks unexpectedly, and turns small issues into late-night incidents. Success is not measured by how many scripts you wrote. It is measured by how many problems your systems solve without you.

What that looks like in my pipelines

  • In the Spring Boot lab, older pipeline runs are cancelled when a newer push arrives, Maven libraries are cached between runs, and only the main branch publishes an image, so untested code never reaches the registry.
  • In the Azure lab, a concurrency group stops two runs changing the same environment at once, and a plan is posted on every pull request so a reviewer sees exactly what will change.
  • Rollbacks are automatic: helm upgrade --install --atomic reverses a release that never becomes ready.

Where I keep a human on purpose

Not everything should be automatic. In the Azure pipeline, the apply job waits in a protected environment until a person approves it. That is a deliberate decision point, not a missing step. Automation should handle the routine and put the judgment calls in front of someone with the information to make them.

Knowledge in one head is a dependency

Many environments have one engineer everyone goes to: they know which server to check, which script to run, and which setting not to touch. That is not just knowledge, it is a dependency. People go on vacation, change teams and leave.

Documentation, runbooks and repeatable processes are how you remove that dependency. Every build in my AWS portfolio has architecture, operations and teardown notes, the trade-offs are written as decision records, and the experiments in my labs are documented with the commands to reproduce them.

The most expensive thing is technical debt

Cloud bills get the attention, but shortcuts cost more over time: skipped documentation, hardcoded configuration, manual steps, and environments only one person understands. Onboarding takes longer, simple changes become risky, and incidents take longer to resolve. Settings that change without a rebuild, and pipelines anyone on the team can read, are cheap ways to avoid it.

Good DevOps is not only shipping quickly. It is building systems your future self and your teammates can work on with confidence months later.
